# Development

## Prerequisites

- Node.js 24
- pnpm, through Corepack. The version is pinned by the `packageManager`
  field in `package.json`; run `corepack enable` once and Corepack provides
  the matching pnpm.

## Running the app

```sh
make dev
```

This installs nothing; run `make deps` first on a fresh checkout. The dev
server listens on http://localhost:5173 and refuses to start if that port is
taken, because sign-in redirects back to that exact address.

Sign-in needs the Yagura API server running on http://localhost:8787 (set
in `packages/apps/web/.env.development`), which serves both the session API
and the activity API, and the GitHub App's client id.
Put the client id in `packages/apps/web/.env.local`, which is not committed:

```sh
VITE_GITHUB_CLIENT_ID=<the GitHub App client id>
```

The GitHub App must list `http://localhost:5173/callback` as one of its
callback URLs; GitHub refuses to redirect anywhere else.

`packages/apps/web/.env.example` lists every variable the app reads.

## Using a deployed session API

The session API keeps the refresh token in a cookie set with `SameSite=Lax`,
so the browser sends it only to a session API on the same site as the app.
Against a deployed API on another site, sign-in appears to succeed but the
session is lost on reload.

Instead, let the dev server proxy the deployed API, so that the app calls
`/session` and `/activity` on its own origin. Put these lines in
`packages/apps/web/.env.local`:

```sh
VITE_GITHUB_CLIENT_ID=<the client id of the GitHub App that API uses>
YAGURA_SESSION_API_PROXY=https://<host of the deployed session API>
```

and point the app at the dev server when starting it:

```sh
VITE_YAGURA_SESSION_API=http://localhost:5173 make dev
```

`VITE_YAGURA_SESSION_API` goes on the command line rather than in
`.env.local` because `.env.development` takes precedence over `.env.local`
and would keep `http://localhost:8787`; a variable set in the environment
takes precedence over both. `YAGURA_SESSION_API_PROXY` is read by the dev
server only and never reaches the app or a build. The deployed API must
allow the origin `http://localhost:5173`, and the GitHub App it belongs to
must list `http://localhost:5173/callback` as one of its callback URLs.

## Running without the Yagura API

```sh
VITE_API_MOCK=1 make dev
```

With `VITE_API_MOCK=1`, the app starts [Mock Service Worker](https://mswjs.io/)
in the browser and answers the session API and the activity API from the
handlers in `packages/testing/api-mocks`, the same ones the tests use: the
session API (signed in as `mock-user`), `GET /activity/organizations` (two
organizations, `mock-labs` and `mock-org`, so that the header shows the
organization selector), and `GET /activity` (the same activity for each:
a few members including the signed-in `mock-user`, and Dependabot as a
bot; their pull requests over the 14 days before the page loaded, with
drafts, pushes, merges of one another's pull requests, a closed one, and
the bot's own pull requests, merged and open). Nothing is fetched from
GitHub.
"Sign in with GitHub" skips the GitHub authorize page and returns straight
to the callback with a mock code, so sign-in completes without leaving
localhost and without a client id, and the page then shows `mock-labs`
(the first by login), its members, and their pull requests. The mock session survives a reload in the
same tab, as the refresh cookie would, until "Sign out". Unlike the cookie, it is kept per tab: another tab needs signing in on its own, and a tab signed out by a sign-out in another tab signs in again when it is reloaded.

The worker script is `packages/apps/web/public/mockServiceWorker.js`,
generated by `msw init`. After upgrading `msw`, regenerate it into the
directory listed under `msw.workerDirectory` in
`packages/apps/web/package.json`:

```sh
pnpm --filter @yagura/web exec msw init
```

The mocks are loaded only in this mode and are not part of the production
bundle.

## Checking changes

```sh
make check
```

This installs dependencies from the lockfile, then runs the build, type
check, tests, lint, format check, and dependency rules across the workspace.
The lint covers every package and the configuration files at the root
(`eslint.config.js` and `.dependency-cruiser.cjs`).
It is the same gate CI runs on every pull request. Run `pnpm format` to fix
formatting.

## Workspace layout

Packages live at `packages/<layer>/<name>`. The layers and what each may
import from the rest of the workspace:

| Layer     | May import                  |
| --------- | --------------------------- |
| `apps`    | anything                    |
| `ui`      | `libs`                      |
| `gateway` | `domain`, `libs`            |
| `domain`  | nothing                     |
| `testing` | `domain`, `gateway`, `libs` |
| `libs`    | nothing                     |

No package imports `apps`, and circular imports are forbidden. The rules are
enforced by dependency-cruiser (`pnpm depcruise`, configured in
`.dependency-cruiser.cjs`).
